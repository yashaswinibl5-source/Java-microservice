PATIENT MANAGEMENT MICROSERVICE – INTERVIEW READINESS DOCUMENT

Project context
- Built a patient management microservice integrated with a billing service using gRPC.
- The system follows a microservice pattern with separate components for:
  - Patient service (REST API + JPA + PostgreSQL)
  - Billing service (gRPC server)
  - PostgreSQL database
  - Docker Compose orchestration
- The goal was to allow patient creation/update to trigger a billing account creation request through gRPC.

1. Core technical concepts (Basic to Advanced)

A. Basic concepts
1. REST API
   - HTTP methods: GET, POST, PUT, DELETE
   - CRUD flow for patient management
   - Example: POST /patients creates a patient record
   - ResponseEntity is used to return proper HTTP status and body

2. Spring Boot
   - Simplifies Java application bootstrapping
   - Auto-configures application components, web server, database integration, etc.
   - @RestController, @RequestMapping, @GetMapping, @PostMapping, @PutMapping, @DeleteMapping

3. Java classes and packages
   - Controller handles incoming API requests
   - Service contains business logic
   - Repository handles database access
   - DTOs transfer data between layers
   - Entity/model represents database record structure

4. JPA / Hibernate
   - Maps Java classes to database tables
   - Handles persistence using Spring Data JPA repositories
   - Entity classes maintain data model

5. PostgreSQL
   - Relational database used to persist patient information
   - Used for stable and structured data storage

6. Validation
   - @Valid and Bean Validation ensure request fields are valid
   - Example: name required, email format valid, dateOfBirth required

B. Intermediate concepts
1. DTO design
   - DTOs separate API contract from persistence model
   - Prevent accidental exposure of internal entity structure
   - Used for request and response handling

2. Layered architecture
   - Controller -> Service -> Repository -> Database
   - Keeps responsibilities separated
   - Easier to maintain and test

3. Dependency injection
   - Spring automatically injects dependencies using constructors
   - Example: PatientService depends on PatientRepository and BillingServiceGrpcClient

4. Environment configuration
   - application.properties or environment variables for runtime config
   - Example:
     - spring.datasource.url
     - billing.service.address
     - billing.service.port
   - Important when running inside Docker containers

5. Docker networking
   - Containers cannot use localhost to talk to other containers
   - Use service names like postgres and billing-service inside Docker network
   - Host port mapping is separate from container internal port mapping

6. gRPC basics
   - gRPC is a high-performance RPC framework built on HTTP/2
   - Uses .proto files to define service contracts
   - More efficient than REST for service-to-service communication

7. Protobuf
   - Protocol Buffers define message structure and service methods
   - Compact, fast, strongly typed
   - Example contract:
     - BillingRequest { patientId, name, email }
     - BillingResponse { accountId, status }

C. Advanced concepts
1. Microservice communication
   - Patient service calls billing service asynchronously/synchronously over RPC
   - Different services own different responsibilities
   - Independence improves scalability and maintainability

2. Service discovery and networking in containers
   - DNS resolution via Docker Compose service names
   - Example: billing-service:9001 is used instead of localhost:9001 inside the container
   - This is critical in a multi-container setup

3. gRPC client/server integration in Spring Boot
   - The patient service acts as a gRPC client
   - Billing service acts as a gRPC server
   - ManagedChannel and blocking stub are used to call methods

4. Runtime startup failures and dependency compatibility
   - A major issue in the project was a gRPC library mismatch
   - Root cause: server and client libraries were not aligned
   - Error example:
     - AbstractMethodError
     - Failed to start bean 'shadedNettyGrpcServerLifecycle'
   - This is a classic example of transitive dependency incompatibility in Java projects

5. Build and dependency management
   - Maven manages versions and transitive dependencies
   - Dependency conflicts can break runtime behavior, even when code compiles
   - BOM / version alignment is essential in multi-module systems

6. Observability and debugging
   - Logs show startup sequence, service initialization, database connection, and gRPC target binding
   - Useful logs:
     - Tomcat started on port 4000
     - HikariPool started
     - gRPC Server started, listening on address: *, port: 9001
   - This helps confirm each layer is healthy

7. Resilience and reliability patterns
   - Correct environment wiring is crucial
   - Rebuilding Docker images ensures stale JARs are not reused
   - Health checks and proper startup ordering help services become reliable

2. Challenges faced during this project

Challenge 1: gRPC startup loop / crash
- Symptom: application kept failing during startup
- Root cause: mismatched gRPC library versions causing AbstractMethodError
- Fix: align dependency versions and rebuild containers

Challenge 2: Docker localhost confusion
- Inside a container, localhost refers to itself, not other containers
- This caused DB and service connection failures
- Fix: use postgres and billing-service service names instead

Challenge 3: Wrong database host / environment config
- App pointed to localhost instead of postgres when running in Docker
- Fix: use environment variables and correct Spring datasource configuration

Challenge 4: gRPC service not visible as expected in IDE / Maven
- The issue was not a missing service class
- It was about understanding the runtime flow: client-service vs server-service distinction
- Fix: separate gRPC client use from server use and verify actual runtime wiring

Challenge 5: Startup ordering and container dependencies
- Services needed PostgreSQL and billing-service to be available before dependent services initialized
- Fix: use Docker Compose health checks and proper environment variables

Challenge 6: Validation handling
- Patient creation required valid ISO date string like 1999-05-15
- Missing or invalid date format caused validation errors
- Fix: pass valid request payloads

3. Technical decisions and design rationale

Why REST for patient API?
- Good for external clients and UI integration
- Easy to test with Postman or curl

Why gRPC for billing call?
- Efficient internal service-to-service communication
- Strong typing via Protobuf
- Better than HTTP JSON for inter-microservice backend calls

Why separate Docker services?
- Isolates workloads and dependencies
- Makes networking explicit and predictable
- Easier to scale and manage

Why align dependency versions?
- Prevent runtime incompatibility and class-loading errors
- Critical for Java projects with transitive dependencies

6. Core interview talking points

Q: What is the difference between REST and gRPC?
A: REST is widely used for external APIs, uses JSON over HTTP, and is easier for browser/mobile clients. gRPC is better for backend service-to-service communication, uses HTTP/2, and is compact and strongly typed via Protobuf.

Q: Why did the app fail to start?
A: There was a dependency mismatch in the gRPC libraries. The server startup expected a method signature that the currently loaded Netty gRPC classes did not implement.

Q: Why did Docker networking fail?
A: localhost inside a container points to itself. We had to use Docker service names like postgres and billing-service to connect correctly.

Q: How did you fix the issue?
A: Aligned dependency versions, removed unnecessary server-side gRPC setup from the patient client, updated environment variables, and rebuilt Docker images.

7. Kafka and event-driven architecture added later

A. Why Kafka was introduced
- Kafka was added to demonstrate asynchronous, decoupled event-driven communication between services.
- The patient service publishes an event when a patient record is created or changed.
- The analytics service subscribes to that event and logs the payload for monitoring/analytics.

B. Kafka terminology
- Producer: sends messages to a Kafka topic.
- Consumer: reads messages from a topic.
- Topic: named stream of events.
- Consumer group: allows multiple consumers to share partitions and balance work.
- Offset: position of a consumer in a topic, used to track message consumption.
- Kafdrop: browser-based UI to inspect Kafka brokers, topics, partitions, and messages.

C. Kafka wiring in this project
- Broker is started in Docker via Apache Kafka container.
- Producer sends JSON strings to the patient topic.
- Consumer in analytics-service listens to the same topic using Spring Kafka.
- Important requirement: use Docker service name kafka:9092 instead of localhost inside containers.
- Important requirement: advertise the internal broker address correctly so consumers and Kafdrop can reach it.

D. Common Kafka problems solved in this project
- Kafka advertisement mismatch: producer/consumer tried to connect using localhost instead of the Docker service.
- Missing Spring listener factory: analytics service failed startup because @EnableKafka and kafkaListenerContainerFactory were missing.
- Invalid offset-reset property: typo in application.properties blocked expected consumer behavior.
- Wrong value deserializer: when producer sends String JSON, consumer must use StringDeserializer.
- Startup race conditions: Kafka may become ready after app startup; health checks and dependency ordering are necessary.

E. Real event flow
1. Client triggers a patient request.
2. Patient service saves record in PostgreSQL.
3. Patient service publishes a JSON message to Kafka topic patient.
4. Analytics service receives the message via @KafkaListener.
5. Consumer logs: "Received event from Kafka" with the JSON payload.
6. Kafdrop can be used to inspect the topic and verify the message exists.

11. Auth service and JWT login flow

A. Purpose
- The auth service handles user authentication and issues JWT tokens.
- It is the next logical layer after the API gateway and is used to protect backend services.
- It verifies credentials against the auth database and returns a signed token for future requests.

B. Flow
1. Client sends POST /login with email and password.
2. AuthController receives the request.
3. AuthService loads the user by email.
4. Password is verified using BCrypt.
5. If valid, JwtUtil generates a JWT token.
6. Client sends that JWT in the Authorization header for protected requests.
7. /validate checks if the token is valid and not expired.

C. Important concepts
- JWT = JSON Web Token, signed token used for stateless auth.
- BCrypt = password hashing algorithm; passwords are never stored in plain text.
- Authorization header: Bearer <token>
- SecurityConfig permits all endpoints for the demo; in production you would secure routes based on roles.

D. Local run guidance
- For normal app work, you do NOT need to run the auth service from your IDE separately if the Docker stack is already running.
- The Docker Compose stack is enough: auth-service runs on port 4006 and the gateway routes it on port 4004.
- Use these URLs for testing:
  - http://localhost:4006/login  (direct auth-service)
  - http://localhost:4004/auth/login  (through API gateway)
- Only run the auth service locally from IDE if you are debugging code changes in the auth module and want direct local execution.
- If running locally, make sure Postgres is up and the datasource env variables point to auth-postgres:5432 or your local DB.

UPDATED SECTION: KAFKA EVENT-DRIVEN COMMUNICATION AND INTER-SERVICE EVENT FLOW

Project update after the latest work
- Added Kafka as an event bus between patient-service and analytics-service.
- patient-service acts as the producer and sends a JSON message to the patient topic when a patient is created.
- analytics-service acts as the consumer and logs the event as soon as it is received from Kafka.
- Kafdrop was also added to visually inspect brokers, topics, partitions, and message data.
- Docker Compose orchestration now includes PostgreSQL, Kafka, Kafdrop, billing-service, patient-service, and analytics-service.

1. Why Kafka was added in this project
- Kafka helps decouple services and enables event-driven architecture.
- Patient creation is now not only saved to the database but also published as an event.
- Other services like analytics, notifications, or reporting can consume this event independently without tightly coupling with the patient service.
- In interview terms: Kafka improves scalability, loose coupling, asynchronous processing, and event replay capability.

2. Kafka core concepts
A. Broker
- Kafka broker stores and manages messages.
- In this project, Kafka runs as a Docker service named kafka.

B. Topic
- A topic is a logical stream of messages.
- We used the patient topic.

C. Producer
- Producer writes messages to a topic.
- In patientservice, kafkaProducer sends JSON strings like:
  {"patientId":"...","name":"...","email":"...","eventType":"PATIENT_CREATED"}

D. Consumer
- Consumer reads messages from a topic.
- In analytics-service, KafkaConsumer listens to the patient topic and logs the payload.

E. Consumer group
- Same group id means multiple consumers share partitions.
- Different group ids mean each consumer sees the stream independently.
- In this project: analytics-service uses group id analytics-service.

F. Partition
- A topic can be split into partitions for scalability.
- Kafka distributes messages across partitions.
- Consumers read from offsets in partitions.

G. Offset
- Offset is the position of a message in a partition.
- Kafka tracks where each consumer group has read up to.

H. Group coordinator
- Kafka uses a coordinator to manage consumer groups.
- A common issue during debugging was NOT_COORDINATOR, meaning the consumer was trying to join a group before the broker was fully ready.

3. Docker and Kafka networking details
- Inside Docker, localhost means the same container, not another service.
- Services must use Docker service names such as kafka:9092 and postgres:5432.
- We corrected the Kafka listener configuration:
  KAFKA_LISTENERS=PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
  KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://kafka:9092
- This allowed container-to-container connection while still exposing Kafka externally via localhost for local access.

4. Kafka configuration in this project
Patient service configuration
- spring.kafka.producer.bootstrap-servers=${KAFKA_BOOTSTRAP_SERVERS:kafka:9092}
- key serializer: StringSerializer

- Producer sends JSON string messages to the patient topic.

Analytics service configuration
- spring.kafka.bootstrap-servers=kafka:9092
- spring.kafka.consumer.group-id=analytics-service
- spring.kafka.consumer.auto-offset-reset=earliest
- key and value deserializer set to StringDeserializer

5. Kafka listener setup and startup fix
Important issue faced
- The analytics service failed to start because Spring could not find a bean named kafkaListenerContainerFactory.
- Root cause: @EnableKafka was missing and no custom listener factory bean was defined.

Fix applied
- Added @EnableKafka on AnalyticsServiceApplication.
- Added KafkaConfig class defining:
  - ConsumerFactory<String, String>
  - ConcurrentKafkaListenerContainerFactory<String, String>
- The consumer method was then registered properly and Spring Kafka started the listener.

6. Consumer method behavior
The analytics consumer is implemented as:
- @KafkaListener(topics = "patient", groupId = "analytics-service")
- method consumerEvent(String message)
- It reads the JSON string using Jackson ObjectMapper.
- It converts it to a Map and logs:
  Received event from Kafka: { ... }

This is a great example of how to consume event-driven data and parse it for downstream analytics or reporting.

7. Why the service initially did not log anything

- Consumer group coordinator not ready (NOT_COORDINATOR)

Once these were fixed, the analytics service successfully subscribed to the topic and consumed events.

11. Practical interview questions for Kafka
Q: What is Kafka?
A: Kafka is a distributed event streaming platform used for high-throughput messaging, logs, and event-driven communication.

Q: Why is Kafka used in microservices?
A: It decouples producers and consumers, supports asynchronous processing, and allows multiple services to react to the same event.

Q: What is a topic?
A: A topic is a named stream of records in Kafka.

Q: What is a consumer group?
A: A consumer group is a set of consumers sharing a topic subscription. They coordinate offsets and partition assignment.

Q: What is the difference between producer and consumer?
A: Producer writes data to Kafka, while consumer reads and processes data.

Q: What is a partition?
A: A partition is a unit of parallelism in Kafka and allows higher throughput.

Q: What is an offset?
A: An offset is the position of a message within a partition.

Q: Why did Docker networking matter here?
A: Kafka was advertising the wrong address internally, so services could not coordinate correctly. Using kafka:9092 fixed the issue.

Q: Why is @EnableKafka important?
A: It enables Spring Kafka listener infrastructure and scanning for @KafkaListener methods.

Q: What is the purpose of kafkaListenerContainerFactory?
A: It defines how Kafka listeners create and use consumer containers.

Q: What is the difference between REST and Kafka?
A: REST is synchronous request-response. Kafka is asynchronous messaging for event-driven integration.

12. Lessons learned from the Kafka integration
- Kafka is not just a queue; it is a streaming platform.
- Docker networking must be configured carefully.
- Correct listener and advertised-listener values are critical.
- Consumer registration requires proper Spring configuration.
- Health checks reduce startup race conditions.
- Event-driven systems are powerful but need clear handling of retries, offsets, and consumer-group behavior.
